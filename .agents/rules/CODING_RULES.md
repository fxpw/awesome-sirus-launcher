# Правила разработки

Эти правила использовать при реализации лаунчера. Подробные project skills лежат в `.agents/skills/`.

Каноническое описание слоев, разрешенных зависимостей и архитектурного чек-листа: [`docs/ARCHITECTURE.md`](../../docs/ARCHITECTURE.md). При расхождении архитектурных формулировок использовать этот документ.

## Общие правила

- После любых изменений проекта агент должен обновить `CHANGELOG.md` или явно указать, почему запись не нужна.
- Если изменение завершает, добавляет или переносит пользовательскую возможность, агент должен обновить её статус в `docs/ROADMAP.md`; `docs/PROJECT_PLAN.md` не использовать как актуальный status-документ.
- При подготовке коммита агент должен использовать `.agents/skills/commit/SKILL.md` и описывать фактические изменения, а не только исходную просьбу.
- Версию релиза хранить в `VERSION`; синхронизировать `VERSION`, `package.json.version` и lockfile.
- Писать на TypeScript везде, где это возможно.
- Держать типы общих DTO в `shared`, чтобы main/preload/renderer/core не расходились.
- Не смешивать UI, IPC и файловую систему в одном модуле. Явное исключение — composition root `src/main/index.ts`: он создаёт окно, собирает сервисы с адаптерами (`spawn`, запись скрипта обновления, диалоги) и регистрирует IPC handlers; новую доменную логику туда не добавлять, а выносить в модуль `src/main/<домен>/`.
- Запись файлов, сеть и запуск процессов делать только в Electron main; `core` может читать файловую систему (проверка наличия путей, чтение `.toc`) и использовать `node:path`, но не импортирует Electron.
- Renderer не должен иметь прямой доступ к Node.js API.
- Все пути хранить как абсолютные, но в логах и UI показывать аккуратно.
- Для путей использовать `path.join`, `path.resolve`, `path.normalize`, не собирать пути строками.
- Сетевые и файловые операции должны поддерживать отмену или хотя бы корректное завершение.
- Скачивание делать через временный файл, затем проверка, затем перемещение.
- Ошибки превращать в понятные доменные ошибки, а не отдавать в UI сырой stack trace.

## Backend / Electron main

- Включить `contextIsolation: true`.
- Не включать `nodeIntegration` в renderer.
- Все IPC-каналы описывать в одном typed контракте.
- IPC handlers должны валидировать входные и выходные данные через Zod-схемы request/response слоя.
- Не доверять данным из renderer.
- Новые долгие операции проектировать под целевую job-модель с `id`, `status`, `progress`, `error` (`docs/ARCHITECTURE.md` §7). Сейчас её нет: прогресс есть у проверки клиента и установки аддонов, отмена — только у проверки клиента.
- Прогресс отправлять событиями main -> renderer.
- MD5 считать потоково, без чтения больших файлов целиком в память.
- Архивы распаковывать только после проверки путей внутри архива, чтобы избежать zip slip.
- GitHub-аддоны в MVP скачивать как zip архива кода, распаковывать во временную папку и переносить в `Interface/AddOns` только реальные папки аддонов с `.toc`, а не верхнюю папку архива.
- Перед перезаписью важных пользовательских данных создавать safety backup.
- Desktop backend flow: `ipc channel -> Zod request/response schema -> handler/controller -> service/core -> adapter`.

## Frontend / Vue

- Новые и переработанные части UI строить слоями `page -> block -> element -> component`.
- `page` собирает сценарий экрана, `block` крупные секции, `element` формы/списки/карточки, `component` переиспользуемые детали.
- Видимый текст выносить в локализацию, а не размазывать строками по компонентам.
- Темы оформлять через общие CSS variables, а не локальные переопределения в каждом блоке.
- Компоненты делать маленькими и предметными.
- Новую ветвящуюся бизнес-логику не класть в `.vue`, выносить в composables или `core`. Сейчас состояние и обработчики главного экрана живут в `src/renderer/pages/DashboardPage.vue`, вкладки аддонов — в `src/renderer/elements/AddonsPanel.vue`; это не образец для нового кода.
- Библиотека сторов не используется: состояние экрана держит страница, переиспользуемое между компонентами состояние — composables в `src/renderer/composables`.
- Не показывать технические исключения пользователю без перевода в понятный текст.
- Все кнопки опасных действий требуют подтверждения: восстановить или удалить backup `WTF`, удалить аддон, аккаунт или FPS-патч, сбросить настройки майнинга, перезаписать файл.
- Прогресс должен быть видимым и не должен прыгать из-за изменения текста.
- UI должен быть плотным и рабочим: это лаунчер, не лендинг.
- Для иконок использовать библиотеку иконок после выбора UI-стека, не рисовать вручную.

## Тестирование

- Unit tests: чистые модули путей, MD5, парсинг API, выбор fallback-источника.
- Portability tests: `tests/portableCore.test.ts` проверяет, что `core` не импортирует `electron`.
- Adapter contract tests: filesystem, downloader, archive extractor, process launcher, secret storage. Сейчас есть для архивов, JSON-файлов и GitHub-загрузчика; для secret storage и process launcher пока нет.
- Integration tests: backup/restore на временной директории.
- UI tests (запланированы, инструментов пока нет): старт приложения, выбор пути, отображение статуса.
- Для опасных файловых операций тесты должны использовать временные директории.
- Перед релизом обязательно прогнать smoke test на чистой папке клиента-копии.

## Версионирование и сборка

- Обычные изменения писать в `CHANGELOG.md` в раздел `[Unreleased]`.
- Релизную версию повышать только отдельным осознанным изменением `VERSION`.
- `version` в `package.json` должен совпадать с `VERSION`.
- GitHub Actions должен проверять приложение на PR и выполнять релизную сборку при изменении релизных файлов.
- Релизные артефакты Windows сохранять как workflow artifacts и публиковать в GitHub Releases.
- Для автообновления лаунчера GitHub Release tag должен совпадать с версией, а release assets должны быть предсказуемо названы.

## Безопасность

- Никогда не выполнять скачанный код.
- Запускать только `run.exe` из провалидированной папки WoW, exe майнера, выбранный пользователем после явного согласия, и скачанное обновление лаунчера после проверки размера и PE-сигнатуры. Произвольные команды и пути запуска из renderer запрещены (подробно — `docs/ARCHITECTURE.md` §4).
- Не распаковывать архивы за пределы целевой директории.
- Не хранить GitHub token в plain config.
- GitHub token для аддонов хранить только как secret через защищенное хранилище ОС и передавать в запросы через `Authorization: Bearer ...`.
- В UI можно показывать факт наличия GitHub token и rate limit, но нельзя показывать сохраненное значение токена.
- Не встраивать GitHub token в клиент для автообновления; публичные релизы предпочтительнее для update flow.
- Не хранить пароли аккаунтов в plain config; использовать защищенное хранилище ОС, если оно доступно.
- Никогда не писать пароли в логи, ошибки, changelog, telemetry или debug output.
- Перед изменением `WTF/Config.wtf` создавать safety backup и менять только строки `SET accountName` и `SET readTerminationWithoutNotice`.
- HTTP-источники помечать как менее надежные. FPS-патч: манифест с MD5 приходит по HTTPS (`https://api.d1st4r.ru/patchfx`); если он недоступен, размер и дата берутся из HEAD-запросов к https-, затем к http-источнику. Если хеш из манифеста известен, первым скачивается зеркало `http://d1st4r.stream`, вторым `https://d1st4r.ru` (он за Cloudflare и с российских адресов зависает); без хеша первым идёт https, а http остаётся запасным. Скачанный файл до замены проверяется по MD5 из манифеста (без манифеста — по размеру из HEAD, если он известен) и по сигнатуре MPQ. Пометки http-источника в UI пока нет.
- Любые destructive операции должны иметь dry-run или подтверждение.

## Стиль кода

- Предпочитать явные имена: `wowPath`, `addonsPath`, `backupArchivePath`.
- Не делать универсальные helper'ы до появления повторения.
- Не добавлять глобальное состояние без необходимости.
- Не глотать ошибку молча: `catch` и `.catch()` допустимы, только если возвращают явное запасное значение (`[]`, `undefined`, состояние «нет данных») или переводят ошибку в доменную; пустой `catch {}` запрещён.
- В логах фиксировать действие, путь, источник и результат.
- Комментарии писать только там, где они объясняют неочевидное решение.
