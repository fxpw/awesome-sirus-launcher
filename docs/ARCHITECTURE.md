# Архитектура Awesome Sirus Launcher

Этот документ — канонический источник архитектурных правил проекта. Он описывает не планы, а обязательные границы модулей и критерии приемки изменений.

Термины:

- **обязательно** — правило нельзя нарушать в обычном изменении;
- **запрещено** — зависимость или поведение не допускается;
- **рекомендуется** — допустимо отступить, если решение остается простым и проверяемым.

Осознанное исключение из обязательного правила должно быть описано в pull request или отдельном ADR в `docs/decisions/`: причина, альтернативы, последствия и план устранения временного решения.

## 1. Цели архитектуры

Архитектура должна обеспечивать:

- безопасность Electron-приложения и пользовательских файлов;
- тестируемую бизнес-логику без запуска Electron;
- возможность заменить Electron-shell, не переписывая доменные правила;
- единый типизированный контракт между main, preload и renderer;
- предсказуемое размещение нового кода;
- локальные изменения: новый сценарий не должен требовать правок несвязанных модулей.

## 2. Слои и разрешенные зависимости

```text
renderer pages / blocks / elements / components
                    |
                    v
          renderer api services
                    |
                    v
              preload bridge
                    |
                    v
       IPC schemas and handlers (main)
                    |
                    v
          main services / adapters
                    |
                    v
                  core

shared contracts <── main / preload / renderer
```

Направление стрелки означает «может вызывать или импортировать».

| Каталог                    | Ответственность                                                                         | Разрешенные зависимости                                                                             |
| -------------------------- | --------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| `src/core`                 | Чистые доменные правила, нормализация, планы операций, вычисления                       | стандартная библиотека без системных побочных эффектов, другие core-модули, чистые типы из `shared` |
| `src/main`                 | Electron main process, orchestration, файловая система, сеть, архивы, процессы, secrets | `core`, `shared`, Node.js, Electron и инфраструктурные библиотеки                                   |
| `src/preload`              | Узкий типизированный мост renderer ↔ main                                               | `shared`, безопасная часть Electron IPC                                                             |
| `src/shared`               | DTO, имена каналов, публичные ошибки и общие контракты                                  | только платформо-независимые типы и данные                                                          |
| `src/renderer/api`         | Типизированный клиент preload API                                                       | `shared`, объявленный preload contract                                                              |
| `src/renderer/pages`       | Сборка пользовательского сценария целого экрана                                         | blocks, elements, components, composables, renderer shared/api                                      |
| `src/renderer/blocks`      | Крупные секции layout или экрана                                                        | elements, components, composables, renderer shared/api                                              |
| `src/renderer/elements`    | Предметные формы, списки, карточки и панели                                             | components, composables, renderer shared/api                                                        |
| `src/renderer/components`  | Малые переиспользуемые UI-компоненты                                                    | renderer shared; без знания конкретного бизнес-сценария                                             |
| `src/renderer/composables` | Переиспользуемое состояние и UI-логика                                                  | renderer api/shared и другие composables без циклов                                                 |

Обязательные ограничения:

- `core` не импортирует `electron`, Node.js API файловой системы, сеть, process launcher или UI.
- `shared` не импортирует `main`, `preload`, `renderer`, `electron`, Vue или Node.js.
- `renderer` не импортирует `main`, `preload`, Node.js API или Electron.
- `preload` не содержит бизнес-логику, файловые и сетевые операции.
- `main` не импортирует Vue-компоненты и renderer-модули.
- Циклические зависимости между модулями запрещены.
- Междоменные импорты должны проходить через явно экспортированный публичный контракт, а не через внутренности соседнего модуля.

## 3. Core: доменная логика

В `src/core/<domain>` размещается код, который отвечает на вопрос «что должно произойти», но сам не обращается к ОС или сети.

В core обязательно размещать:

- проверку и нормализацию входных данных домена;
- построение безопасных путей и планов файловых операций;
- парсинг и нормализацию внешних manifest/API-моделей;
- сравнение версий, MD5 и состояний;
- правила выбора fallback-источников;
- преобразование доменных ошибок в стабильные коды.

Core-функция должна получать данные и зависимости явно и возвращать результат без скрытого глобального состояния. Для времени, случайности или внешнего состояния использовать параметры или интерфейсы, если это влияет на тест.

В core запрещено:

- читать или писать файлы;
- выполнять HTTP-запросы;
- запускать процессы;
- обращаться к `ipcMain`, `BrowserWindow`, `dialog`, `safeStorage`;
- читать `window`, DOM или Vue state;
- возвращать Electron-, Node.js- или Vue-специфичные объекты.

Каждое новое или измененное доменное правило обязательно покрывается unit-тестом.

## 4. Main process: orchestration и адаптеры

`src/main` — единственное место, где разрешены привилегированные системные операции.

Main service обязан:

1. получить уже провалидированный запрос из IPC handler;
2. вызвать core для доменных решений;
3. выполнить план через узкие инфраструктурные функции или адаптеры;
4. преобразовать ожидаемые ошибки в публичную ошибку/DTO;
5. вернуть plain object, пригодный для structured clone и проверки Zod-схемой.

Правила:

- Пути собирать только через `path.join`, `path.resolve` и `path.normalize`.
- Перед записью проверять, что целевой путь находится внутри разрешенного корня.
- Скачивать во временный файл, проверять результат и только потом атомарно заменять целевой файл, где это возможно.
- Перед перезаписью `WTF`, `Config.wtf` и других важных пользовательских данных создавать safety backup.
- Архивы проверять на absolute paths и path traversal до извлечения.
- Большие файлы хешировать и архивировать потоково.
- Секреты хранить через защищенное хранилище ОС; запрещено писать их в settings, логи и тексты ошибок.
- Запускать только валидированный игровой executable или явно настроенный сценарий продукта; произвольные команды из renderer запрещены.
- Сетевые и файловые операции должны корректно обрабатывать частичный результат, отмену и повторный запуск.
- Неожиданная ошибка логируется с техническим контекстом в main, но renderer получает безопасное пользовательское сообщение и стабильный код.

Если сервис разрастается, orchestration отделяется от инфраструктуры: например, `addonService` координирует сценарий, а download/archive/file adapters выполняют операции.

## 5. IPC и preload: граница доверия

Канонический путь запроса:

```text
renderer api
  → preload method
  → named IPC channel
  → Zod input schema
  → handler
  → main service / core
  → Zod output schema
  → plain DTO
  → renderer
```

Для каждого нового IPC-метода обязательно:

1. добавить имя канала и TypeScript request/response DTO в `src/shared/contracts.ts`;
2. добавить входную и выходную Zod-схемы в `src/main/ipc/schemas.ts`;
3. зарегистрировать handler через общий schema-first helper;
4. добавить узкий метод в `src/preload/index.ts`;
5. отразить метод в типе `window.launcher` в `src/preload/global.d.ts`;
6. вызывать его из renderer через `src/renderer/api`, если сценарий используется более чем в одном месте или требует преобразования ошибок;
7. покрыть схемы и значимое поведение тестами.

Правила безопасности:

- `contextIsolation` обязательно включен.
- `nodeIntegration` обязательно выключен.
- Renderer считается недоверенной стороной; все входные данные валидируются в main.
- Выходные данные handler также валидируются.
- Preload экспортирует только перечисленные методы продукта, а не `ipcRenderer`, произвольное имя канала или общий доступ к файловой системе.
- Через IPC передаются DTO. Запрещено передавать классы, `Error`, stream, buffer больших файлов, file handles и объекты Electron.
- Имена каналов и DTO не дублируются строками в нескольких слоях.

## 6. Renderer: UI и состояние

Renderer отвечает за представление и пользовательское взаимодействие, а не за системные или доменные решения.

Иерархия UI:

```text
page → block → element → component
```

- `page` собирает полный сценарий экрана и связывает крупные состояния;
- `block` отвечает за крупную секцию layout или экрана;
- `element` реализует предметную локальную зону: форму, таблицу, карточку, панель;
- `component` — небольшой переиспользуемый UI-примитив без привязки к одному домену.

Правила:

- `.vue` содержит представление и локальное взаимодействие; ветвящуюся бизнес-логику выносить в composable/store/core.
- IPC-вызовы централизовать в `src/renderer/api`; прямой `window.launcher` в presentation-компонентах не рекомендуется.
- Публичные DTO брать из `shared`; запрещено вручную дублировать backend response types.
- Видимые строки хранить в i18n. Русский — локаль по умолчанию.
- Состояние, совместно используемое несколькими несвязанными компонентами, размещать в Pinia store по домену. Локальное состояние не поднимать в store без необходимости.
- Для каждого удаленного сценария предусмотреть состояния: loading, ready, empty, running, success, recoverable error и disabled.
- Долгая операция показывает прогресс или текущий этап и блокирует конфликтующие действия.
- Опасное действие требует явного подтверждения.
- Пользователь видит понятное сообщение; технические детали остаются в логах.
- Общий внешний вид задается токенами/CSS variables, а не копированием значений по компонентам.

## 7. Долгие операции и события

Проверка клиента, скачивание, установка, backup/restore и обновление должны моделироваться как операция с явным жизненным циклом:

```text
queued → running → succeeded
                 ↘ failed
                 ↘ cancelled
```

Минимальные данные операции: `id`, `type`, `status`, `progress`, текущий этап и безопасная ошибка.

Обязательно:

- прогресс main → renderer передавать через конкретный типизированный event channel;
- отмену делать кооперативной через `AbortSignal` или эквивалентный контроллер;
- игнорировать запоздалые события от предыдущего `jobId`;
- после ошибки или отмены оставлять файловую систему в согласованном состоянии;
- явно определять, допускаются ли повторный запуск и параллельные операции одного типа.

## 8. Ошибки, логирование и секреты

- Ожидаемые сбои оформлять доменными кодами ошибок: например, invalid path, network unavailable, checksum mismatch, cancelled.
- Не использовать текст исключения как программный контракт.
- Не показывать renderer сырой stack trace.
- Лог должен содержать действие, источник/безопасный путь, результат и correlation/job id для долгих операций.
- Пароли, GitHub token, authorization headers и содержимое защищенного account config запрещено логировать на любом уровне.
- Перед логированием внешнего ответа удалять чувствительные поля.

## 9. Тестовая стратегия

Изменение считается архитектурно завершенным, когда тест находится на самом нижнем подходящем уровне:

| Что проверяется                                          | Тип теста                                |
| -------------------------------------------------------- | ---------------------------------------- |
| Доменное правило, parser, path plan, version/MD5 compare | unit test core                           |
| Zod request/response contract                            | IPC schema test                          |
| Файловая операция, archive, backup/restore               | integration test во временной директории |
| Adapter filesystem/download/archive/process/secrets      | contract test с fake/mock зависимостями  |
| Composable/store с ветвлением                            | renderer unit test                       |
| Критичный пользовательский путь                          | Electron/Playwright smoke test           |

Обязательные правила:

- Unit-тесты не зависят от живых API, реального WoW-клиента и пользовательских директорий.
- Опасные файловые тесты работают только во временной директории.
- Исправление security/data-loss/path-traversal ошибки обязательно получает regression test.
- `tests/portableCore.test.ts` должен продолжать подтверждать отсутствие Electron-зависимостей в core.
- Перед завершением обычного изменения запускается `npm run check`; для изменения сборки или интеграции Electron также `npm run build`.

## 10. Куда помещать новый код

| Вопрос                                                                           | Место                                             |
| -------------------------------------------------------------------------------- | ------------------------------------------------- |
| Это правило можно вычислить из входных данных без ОС и сети?                     | `src/core/<domain>`                               |
| Код читает файлы, скачивает, распаковывает, хранит секрет или запускает процесс? | `src/main/<domain>` или инфраструктурный adapter  |
| Тип используется по обе стороны IPC?                                             | `src/shared`                                      |
| Это проверка входа/выхода IPC?                                                   | `src/main/ipc/schemas.ts`                         |
| Это безопасный метод, доступный браузерному UI?                                  | `src/preload`                                     |
| Это вызов backend из UI?                                                         | `src/renderer/api`                                |
| Это состояние/логика нескольких UI-частей?                                       | Pinia store или `src/renderer/composables`        |
| Это целый экран, крупная секция, предметная зона или примитив?                   | соответственно page, block, element или component |

Если код одновременно подходит в несколько строк, его нужно разделить по границе данных: чистое решение в core, побочный эффект в main, отображение в renderer.

## 11. Архитектурный чек-лист изменения

Перед приемкой изменения проверить:

- [ ] Доменное правило находится в core и тестируется без Electron.
- [ ] Системные побочные эффекты находятся только в main.
- [ ] Общие DTO и каналы определены в shared один раз.
- [ ] IPC проверяет request и response через Zod.
- [ ] Preload предоставляет узкий метод, а не общий системный доступ.
- [ ] Renderer не импортирует Node.js/Electron и не дублирует DTO.
- [ ] UI соблюдает `page → block → element → component`.
- [ ] Опасные операции подтверждаются и создают safety backup, где требуется.
- [ ] Пути, архивы, скачивания, секреты и логи соответствуют правилам безопасности.
- [ ] Есть тест на новое правило или regression-сценарий.
- [ ] Выполнен `npm run check`, а при необходимости `npm run build`.
- [ ] Обновлен `CHANGELOG.md` либо явно зафиксировано, почему запись не нужна.
